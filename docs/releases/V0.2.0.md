# Chordrift v0.2.0

Released 2026-08-29.

v0.2.0 turns the existing CLI into the first client of a provider-neutral Rust
application core without discarding the maintenance workflow proven in v0.1.4.
It is the release foundation for onboarding, library audits, recipes, and
deterministic Spins; hosted and native clients remain later releases.

## What is included

- One versioned command/query/event contract and application facade behind the
  complete maintenance CLI.
- Account-owned, provider-qualified domain identities and explicit provider and
  evidence capabilities.
- Read-only onboarding capture plus inventory-only and enriched audits.
- Provider-neutral Discovery + Rediscovery recipe execution and exact,
  reproducible Spin previews.
- Explicit `maintenance` and `spin_publication` plan origins.
- A machine-readable binary capability handshake and capability-checked intake
  helpers.
- Enumerated ordinary playlist additions: an addition cannot replace full live
  membership or silently restore a manually removed track.
- Additive migrations 0046 and 0047 for the product domain and Spin publication
  identity.
- Provider-neutral fake execution and verification for approved Spin plans.

## Deliberate limits

- Spin publication has no production Spotify mutation adapter in v0.2.0. Its
  planning and safety model is implemented and tested with a fake provider.
- The `product` CLI remains an explicit provider-free rehearsal surface. Its
  database-backed commands require `CHORDRIFT_PRODUCT_REHEARSAL=1`.
- Apple Music is not included. A future adapter must implement the current
  provider-neutral capability boundary rather than revive the old prototype.
- Chordrift still requires an exact inspected plan, readiness assessment, and
  explicit confirmation before it writes to Spotify.

## Upgrade

Back up the database before changing either side of the deployment. A general
installation can then install the locked release:

```console
$ cargo install chordrift --version 0.2.0 --locked --force
$ chordrift --version
chordrift 0.2.0
```

`chordrift db migrate` applies migrations 0046 and 0047; it does not call or
write a provider. Inspect `chordrift db status` before and after migration.

For the verified personal deployment, do not migrate the former 45/45 database
in place. Pair the released v0.2.0 binary with the independently restored,
migrated, and parity-checked 47/47 candidate as one cutover. Keep the former
binary/config/database set intact until read-only post-cutover checks pass.
Follow [Recovery and rollback](../how-to/RECOVERY_AND_ROLLBACK.md).

## Historical compatibility

The `v0.1.4` tag preserves the exact former source and documentation. v0.2.0
retains its safety outcomes and ordinary maintenance commands through adapters;
compatibility does not force old internal ceremony into the new application
architecture.
